## Overall Impression

A real, functioning admin product with genuine architectural discipline (permission-driven nav, honest delta badges, graceful degradation instead of page crashes) undercut by inconsistent adoption of its own conventions — the shared DataTable and StatCard patterns exist but aren't used everywhere, and the app never wired up the feedback loop (toasts, loading states) it already installed the plumbing for. The single biggest opportunity: close the gap between documented conventions and actual usage before adding anything new.

## What's Working

1. **`src/components/dashboard-sidebar.tsx`** — permission-driven nav keyed off live `permissions: string[]`, not a hand-maintained role map. Prevented a real class of bugs (Leaves hidden from Incharge despite holding the permission).
2. **`src/components/delta-badge.tsx`** — renders a neutral "New" pill instead of a fabricated percentage when there's no honest baseline. Directly enforces the product's "trustworthiness through precision" principle at the component level.
3. **Graceful degradation over page crashes** — across ~12 pages, auxiliary dropdown fetches are gated on the exact permission their endpoint requires instead of 403ing the whole page.

## Priority Issues

**[P1] Zero system-status feedback on mutations and navigation**
- Why it matters: no loading.tsx/Suspense anywhere in ~58 routes; Toaster is mounted app-wide but has zero toast.success/error call sites. Office staff processing fee payments all day get no confirmation beyond a dialog closing.
- Fix: add loading.tsx (using the installed Skeleton primitive) to heavy list routes; wire toast.success/error into FormDialog and ConfirmActionButton's result branches.
- Files: `src/components/form-dialog.tsx`, `src/components/confirm-action-button.tsx`
- Suggested command: `/impeccable harden`

**[P1] Label/control association broken for every Select field (~20 sites)**
- Why it matters: `<Label>` without `htmlFor` paired with a `<Select>` with no matching `id` — clicking the label does nothing, and a screen reader gets no accessible name on the exact field being filled. The adjacent `<Input>` fields in the same files do this correctly, proving the pattern is known.
- Fix: add `id` to every SelectTrigger and matching `htmlFor` on its Label; add aria-label to the two bare search inputs.
- Files: discounts/create-dialog.tsx, substitutions/assign-dialog.tsx, homework/create-dialog.tsx, leaves/create-dialog.tsx, incharge-scopes/scope-dialogs.tsx, promotions/filters.tsx, teacher-assignments/assignment-dialogs.tsx, students/[studentId]/enrollment-dialogs.tsx, data-table.tsx, students/search-box.tsx
- Suggested command: `/impeccable audit`

**[P2] Two incompatible "KPI stat card" implementations**
- Why it matters: institute-overview.tsx's StatCard (rounded-xl, ring-1, gap-3, tabular-nums) vs. three Report Center pages hand-rolling the same concept as plain divs (rounded-lg, border, gap-4, no tabular-nums, no DeltaBadge) — the same UI element looks different depending which screen you're on.
- Fix: extract one StatCard/ReportStatTile, reuse across all four locations.
- Files: institute-overview.tsx, reports/financial/page.tsx, reports/academic/page.tsx, reports/attendance/page.tsx
- Suggested command: `/impeccable layout`

**[P2] Section-heading weight/margin drift at the same hierarchy level**
- Why it matters: identical `<h2>` section headers use font-medium/mb-4 on the student detail page vs. font-semibold/mb-3 on every Reports page — no canonical "section heading" style, so it keeps drifting per page.
- Fix: a SectionHeading component or a documented class combo in DESIGN.md.
- Files: students/[studentId]/page.tsx, reports/financial/page.tsx, reports/academic/page.tsx, reports/attendance/page.tsx
- Suggested command: `/impeccable typeset`

**[P3] DataTable (documented as "reused everywhere") is used on exactly one page**
- Why it matters: Campuses, Academic Years, Classes, Sections, Subjects, Teachers, Invoices, Users, Leaves, Complaints all hand-roll a bare Table with no search/sort/pagination — including datasets (Invoices, Users, Complaints) that most need it.
- Fix: migrate those list pages onto DataTable (or a server-side /search pattern where warranted).
- Suggested command: `/impeccable polish`

## Persona Red Flags

**Alex (Power User)**: PRODUCT.md promises command palettes/keyboard shortcuts — none exist anywhere (grep-confirmed). Marking attendance requires opening a dropdown per student for any non-default status. DataTable hardcodes pageSize=8 with no page-size control. No search/sort on Users, Invoices, Complaints, Leaves.

**Sam (Accessibility-Dependent)**: The ~20 unlabeled Select fields mean no accessible name on most create/assign dialogs. DataTable's sortable column headers toggle via a plain button with no `aria-sort` — sort-state changes are never announced. Inline dialog errors have no role="alert"/aria-live (the login form does this correctly via aria-describedby, proving the pattern exists but isn't propagated).

**Priya (Parent, mobile)**: The portal nav is 8 pills in a horizontally-scrolling row with no visible cue that it scrolls — at 400px width "Complaints" is off-screen with no affordance. ChildSwitcher is a bare Select (no photo/grade context) with a full page reload on every switch, and the selected child is only shown inline below each page's h1, never pinned in the header — she re-orients "whose data am I on" on every single page load. The universal lack of loading feedback is worst here: a blank screen on mobile data can't absorb a glanceable check-in.

## Minor Observations

- login/page.tsx's sign-in card uses shadow-sm — the only drop-shadow in the whole codebase vs. the ring-based Card used everywhere else.
- Report pages' hand-rolled stat numbers aren't tabular-nums (institute-overview's StatCard is) — digits can misalign as values change.
- reports/financial/page.tsx colors any nonzero cash-closing "Variance" as destructive regardless of sign — a positive variance reads exactly as alarming as a shortfall.
- All 11 portal pages hand-roll the h1+p header pattern instead of reusing page-header.tsx — no live bug today, but a latent lockstep-edit risk.

## Questions to Consider

1. DataTable is documented as "reused everywhere" but used on one page — was the frontend rebuild actually rolled out everywhere, or did the documentation get ahead of the code?
2. Toaster is mounted specifically so every mutation could confirm itself, and nothing calls it — is silent success the intended UX, or an unclaimed TODO?
3. PRODUCT.md puts this product in Stripe/Linear/Vercel's register partly on "command palettes, keyboard shortcuts" — none exist today. Is that a roadmap commitment, or should the copy be walked back to match what's shipped?
